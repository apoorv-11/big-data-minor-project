# FraudShield — Problem Statement

## Domain
**Financial fraud detection** in mobile money transfer systems. Mobile payments
are growing rapidly worldwide, and so are the attack vectors: criminals use
synthetic identities, money mules, and fast cash-out chains to drain accounts
before the victim or the operator notices.

## Problem
Fraudulent transactions in mobile-money platforms are **extremely rare**
(~0.13 % of all transactions in our dataset) and deliberately designed to
blend in with legitimate activity. Traditional rule-based systems (e.g. the
`isFlaggedFraud` column in PaySim) catch only a tiny fraction of actual
fraud. A data-driven approach is needed that can:

1. Process millions of transactions efficiently (Big Data scale).
2. Learn patterns that distinguish fraud from legitimate behaviour.
3. Prioritise **recall** (catching real fraud) while keeping precision
   acceptable, because missing a fraudulent transaction is costlier than
   a false alert.

## Objectives
| # | Objective |
|---|-----------|
| 1 | Build a **medallion-architecture pipeline** (Bronze → Silver → Gold) in PySpark that ingests, cleans, validates, and enriches transaction data. |
| 2 | Engineer fraud-relevant features using PySpark window functions, joins, and aggregations. |
| 3 | Train and compare **Logistic Regression, Random Forest, and GBT classifiers** (Spark MLlib) with time-based train/test split and class-weight handling. |
| 4 | Evaluate models primarily on **PR-AUC** (not accuracy, which is misleading at 99.87 % negative rate). |
| 5 | Demonstrate **near-real-time scoring** via Kafka streaming + Structured Streaming. |
| 6 | Serve analytics and model results through an interactive **Streamlit dashboard**. |
| 7 | Automate the pipeline with **Airflow** and a **Makefile** fallback. |

## Target Users
- **Fraud analysts** at a payments company who review alerts and escalate
  cases for investigation.
- **Risk managers** who need aggregate dashboards showing fraud trends by
  transaction type, time of day, and destination account risk.
- **Data engineers** who maintain and extend the pipeline.

## Success Metrics
| Metric | Target | Rationale |
|--------|--------|-----------|
| PR-AUC | > 0.90 | Primary metric for imbalanced binary classification. |
| Recall | > 0.80 at chosen threshold | Missing fraud is costlier than false positives. |
| Pipeline reproducibility | One-command run | `make all` or `python -m src.pipeline.run_all` must re-create every layer from raw data. |
| Dashboard completeness | 6 tabs/pages with live data | No hardcoded or mock numbers. |

## Dataset
**PaySim** — a synthetic dataset generated by a simulator calibrated on a
real mobile-money service in an African country.

> Lopez-Rojas, E.A., Elmir, A., & Axelsson, S. (2016). "PaySim: A financial
> mobile money simulator for fraud detection." *28th European Modeling and
> Simulation Symposium (EMSS)*. Larnaca, Cyprus.

- **Kaggle URL:** https://www.kaggle.com/datasets/ealaxi/paysim1
- **Size:** ~6.36 million transactions, ~470 MB CSV.
- **Time span:** 743 hourly steps ≈ 30 simulated days.
- **Columns:** `step`, `type`, `amount`, `nameOrig`, `oldbalanceOrg`,
  `newbalanceOrig`, `nameDest`, `oldbalanceDest`, `newbalanceDest`,
  `isFraud`, `isFlaggedFraud`.
- **Fraud rate:** ~0.13 % (8,213 fraud cases out of 6,362,620 total).
- **Fraud types:** Only `TRANSFER` and `CASH_OUT` contain fraudulent
  transactions.

## Known Limitations
1. **Synthetic data** — patterns may not fully represent real-world fraud.
   Model performance on production data could differ significantly.
2. **Only two fraud-bearing types** — the model cannot detect fraud in
   `CASH_IN`, `PAYMENT`, or `DEBIT` transactions because none appear in
   the training data.
3. **No temporal seasonality** — the simulation runs for only 30 days,
   so weekly/monthly patterns are not captured.
4. **No customer demographics** — the dataset contains no age, location,
   or device information that real fraud systems would use.
5. **Balance-error features are highly predictive** — `errorBalanceOrig`
   and `errorBalanceDest` may be artefacts of the simulator. If scores
   look "too good", this is a likely reason and should be disclosed.
